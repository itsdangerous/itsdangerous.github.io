문서 천 개를 처리하는 자동화가 있다고 하자. 파일을 읽고, 외부 API로 내용을 분석하고, 결과를 저장한 뒤 사용자에게 완료 알림을 보낸다.

각 단계는 어렵지 않다. 파일 몇 개로 테스트하면 잘 돌아가고, 반복문을 붙이면 대량 처리도 된다.

그런데 731번째 문서에서 응답이 끊겼다.

앞의 730개는 어디까지 끝났을까. 분석만 끝난 문서도 있을 테고, 결과까지 저장된 문서도 있을 것이다. 731번째 문서는 정말 처리되지 않은 걸까, 처리는 끝났는데 응답만 받지 못한 걸까. 프로그램을 다시 실행하면 이미 보낸 알림까지 또 나가는 건 아닐까.

자동화를 다시 실행하기 전에 이 질문부터 확인해야 한다면, 복구에는 여전히 사람이 필요하다.

나는 자동화 설계를 검토할 때 이 장면을 먼저 떠올리는 편이 좋다고 생각한다. 정상적으로 끝나는 경로만 보면 감춰지는 문제가, 중간에 한 번 멈춰보면 드러난다.

**이어서 실행해도 되는가. 그리고 그 판단을 무엇으로 할 것인가.**

아래에서는 이 문서 처리 상황을 바탕으로 실패 이후의 동작을 설계해본다.

## 예외를 잡았지만, 작업을 복구할 수는 없었다

처음 떠올릴 수정은 파일마다 예외를 잡는 것이다.

```python
# 실패 범위를 설명하기 위한 예시
for document in documents:
    try:
        result = analyze(document)
        save_result(document, result)
        send_notification(document)
    except Exception:
        logger.exception("문서 처리 실패: %s", document.id)
```

이렇게 하면 한 문서 때문에 반복문 전체가 멈추지는 않는다. 서로 독립적인 문서를 처리하는 상황에서는 필요한 개선이다.

하지만 실행이 끝나고 실패한 문서만 다시 처리하려고 하면 막힌다.

어느 단계에서 실패했는지는 로그를 읽어야 한다. 결과 저장까지 성공하고 알림에서 실패했다면 분석을 다시 할 필요가 없는데, 코드에는 그 차이가 없다. 프로세스가 강제 종료되면 예외 처리 자체가 실행되지 않을 수도 있다.

여기서 필요한 것은 작업의 진행 상태를 프로세스 밖에 남기는 일이다. 로그에는 원인을 조사할 정보를 남기고, 저장된 작업 상태에는 다음 실행이 무엇을 해야 하는지 남긴다.

그렇다고 문서 처리의 모든 함수 호출을 상태로 만들 필요는 없다. 다시 실행했을 때 비용이 크거나, 중복 실행이 문제가 되거나, 외부에 결과가 남는 지점부터 나누면 된다.

이 사례에서는 분석 결과를 확정하는 단계와 알림을 전달하는 단계를 분리할 만하다. 알림 전송 실패 때문에 이미 끝난 분석까지 반복할 이유가 없기 때문이다.

## 타임아웃 이후에는 성공 여부를 모른다

외부 API 호출에서 특히 조심해야 하는 부분이다.

다음 두 상황은 호출한 쪽에서 모두 타임아웃으로 보일 수 있다.

```text
A. 요청이 서버에 도착하지 않았다.
B. 서버가 처리를 완료했지만 응답이 돌아오지 않았다.
```

A는 다시 보내면 된다. B는 다시 보냈을 때 같은 작업이 한 번 더 수행될 수 있다.

따라서 타임아웃을 곧바로 `failed`로 기록하고 새 요청을 보내는 것은, 확인되지 않은 결과를 실패로 확정하는 판단이다. 외부 작업이 과금되거나 알림·결제처럼 되돌리기 어려운 효과를 만든다면 이 차이가 중요하다.

대응은 상대 시스템이 제공하는 기능에 달려 있다. 요청 식별자로 처리 상태를 조회할 수 있다면 조회해서 결과를 맞춘다. 멱등성 키를 지원한다면 같은 키로 재시도한다. 둘 다 없다면 자동 재시도로 중복 실행을 막겠다는 보장은 할 수 없다. 결과 확인이 필요한 상태로 남겨야 할 수도 있다. [AWS Builders’ Library의 멱등성 API 설명](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

이 사례에서도 외부 분석 API의 응답이 끊겼다면, 해당 문서를 다른 문서의 실패와 똑같이 취급하지 않는다. 다른 문서는 계속 처리하되, 이 문서는 외부 요청 식별자를 가지고 결과 확인을 기다리게 한다.

## 재시도할 때도 같은 작업이어야 한다

재시도를 붙이기 전에 “같은 작업”의 기준부터 정해야 한다.

문서 ID만 사용하면 수정된 문서를 다시 분석하는 요청까지 중복으로 취급할 수 있다. 반대로 매 시도마다 새 UUID를 만들면 재시도라는 사실을 알아볼 수 없다.

이 문서 처리에서는 다음처럼 구분할 수 있다.

```text
논리적 작업: document-42 / revision-7 / analysis-v3
첫 번째 시도: attempt-a
두 번째 시도: attempt-b
```

문서와 분석 조건이 같은 재시도는 논리적 작업 ID를 유지한다. 사용자가 문서를 수정하거나 분석 조건을 바꾸면 새 작업이 된다. 의도적으로 같은 조건의 분석을 새로 수행할 수 있는 서비스라면, 그 요청을 구별할 실행 세대도 필요하다.

그리고 식별자만 정했다고 중복 방지가 끝나지는 않는다.

```python
# 동시 실행을 막지 못하는 예시
if not result_exists(operation_id):
    result = analyze(document)
    save_result(operation_id, result)
```

두 워커가 동시에 조회하면 둘 다 “결과 없음”을 보고 분석을 시작할 수 있다. 작업을 선점하는 과정에는 원자적인 조건부 갱신 같은 장치가 필요하다. 결과 테이블의 유일성 제약은 중복 저장을 막을 수 있지만, 이미 두 번 호출한 외부 API의 실행까지 취소해주지는 않는다.

워커가 죽는 경우도 생각해야 한다. 작업을 영구히 선점하게 두면 복구되지 않는다. 선점에 만료 시간을 두면 다른 워커가 이어받을 수 있지만, 늦게 돌아온 이전 워커가 결과를 덮어쓰는 문제가 생긴다. 그래서 완료 기록에도 현재 선점 토큰이 맞는지 확인하는 조건을 둔다.

이 조건 역시 보호 범위는 내부 상태까지다. 오래된 워커가 외부 서비스를 호출하는 것까지 막으려면 외부 시스템의 멱등성 지원 등 별도 장치가 필요하다.

재시도 안전성은 한 줄짜리 중복 검사로 해결되지 않는다. 어떤 효과를 어느 경계 안에서 한 번만 반영할지 정해야 한다.

## 결과 저장과 알림 사이에도 틈이 있다

분석이 끝나면 결과를 DB에 저장하고 큐에 알림 작업을 넣는다고 하자.

```text
결과 저장 성공
    ↓
프로세스 종료
    ↓
알림 작업 등록 안 됨
```

순서를 바꿔도 문제가 남는다. 알림 작업을 먼저 등록하면 결과 저장이 실패했는데 알림 워커가 먼저 실행될 수 있다.

DB와 메시지 큐에 각각 기록하는 두 동작은, 코드에서 붙여 썼다고 함께 성공하는 것이 아니다.

이 경우에는 결과와 “알림을 보내야 한다는 기록”을 같은 DB 트랜잭션에 저장할 수 있다. 별도 전달자가 그 기록을 읽어 큐에 보내는 방식이 transactional outbox다. 결과만 저장되고 알림 의도가 사라지는 틈을 줄여준다.

다만 전달자가 큐에 보낸 직후 죽으면 같은 기록을 다시 보낼 수 있다. 따라서 outbox를 쓴 뒤에도 소비자는 중복 전달을 처리해야 한다. 최종 알림 서비스가 중복 방지 기능을 제공하는지도 별도로 확인해야 한다. [Transactional outbox 패턴 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

이렇게 나누면 알림이 지연되더라도 분석 결과는 보존된다. 운영자는 분석을 다시 돌리는 대신 남아 있는 알림 작업을 확인하면 된다.

## 실패한 일을 전부 다시 시도하면 장애가 커진다

파일 형식이 잘못된 문서는 기다려도 정상 파일이 되지 않는다. 인증 설정이 틀렸다면 문서마다 같은 요청을 반복해도 해결되지 않는다.

이 사례의 재시도 정책은 오류 메시지보다 다음 행동을 기준으로 나누는 편이 낫다.

| 상황                       | 다음 행동                                |
| -------------------------- | ---------------------------------------- |
| 지원하지 않는 파일 형식    | 해당 문서 처리를 종료하고 입력 수정 요청 |
| API 사용량 제한            | 서버 안내와 재시도 예산에 따라 대기      |
| 응답 유실로 처리 결과 불명 | 상태 조회 또는 같은 멱등성 키로 재시도   |
| 공통 인증 설정 오류        | 같은 의존성을 사용하는 작업 일시 중단    |
| 예상하지 못한 코드 오류    | 원인 확인을 위해 격리하고 반복 실행 제한 |

잠깐의 장애에는 재시도가 도움이 된다. 하지만 서버가 과부하 상태라면 재시도도 추가 부하다. 재시도 간격을 늘리고 무작위 지연을 섞는 이유가 여기에 있다. 재시도 횟수와 전체 처리 기한도 제한해야 한다. SDK와 애플리케이션이 각각 재시도하면 실제 호출량이 예상보다 늘 수 있으므로 어느 계층이 책임질지도 정한다. [Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

작업 큐가 있다는 이유로 처리량 문제가 사라지지도 않는다. 처리 속도보다 유입 속도가 빠르면 대기 작업은 계속 쌓인다. 동시 실행 수와 외부 API 호출량을 제한하고, 감당할 수 없는 요청은 접수 단계에서 늦추거나 거절할 수 있어야 한다.

제목의 “전체 작업이 멈추지 않게”도 무조건 계속 실행하라는 뜻으로 읽으면 곤란하다. 독립적인 파일 하나의 오류는 격리할 수 있지만, 공통 인증이나 저장소가 고장 났다면 해당 작업들을 잠시 멈추는 편이 낫다.

어디까지 계속할 수 있는지는 업무의 의존관계가 결정한다. 천 개의 문서를 개별 분석하는 작업과, 천 개가 모두 있어야 완성되는 하나의 보고서는 완료 조건부터 다르다.

## 부분 성공을 성공으로 숨기지 않기

개별 처리를 분리한 다음에는 사용자에게 무엇을 보여줄지 남는다.

예를 들어 분석 성공 970개, 입력 오류 20개, 재시도 대기 10개라면 “처리 완료”라고만 표시하기 어렵다. 아직 자동으로 이어질 작업이 남아 있기 때문이다. 분석이 끝난 문서의 알림도 일부 대기 중일 수 있다.

이 사례라면 분석 진행과 알림 전달을 별도로 보여주겠다. 전체 상태는 완료된 개수뿐 아니라 앞으로 수행할 작업이 남아 있는지에 따라 결정한다.

실패 항목 목록에는 문서 ID와 오류 설명 외에도 다음 행동이 있어야 한다. 자동 재시도를 기다리면 되는지, 파일을 수정해야 하는지, 운영자가 외부 처리 결과를 확인해야 하는지 구분해야 한다.

관측 지표도 같은 관점에서 고른다. 성공률만 보면 대부분의 문서가 처리되고 있다는 사실은 알 수 있어도, 특정 문서 하나가 몇 시간째 대기 중인지는 놓칠 수 있다. 가장 오래된 미완료 작업의 나이, 결과 확인 대기 수, 재시도 소진 건수도 함께 봐야 한다.

실패한 작업을 별도 큐에 옮기는 것만으로 복구가 끝나지는 않는다. 누가 확인하고, 어떤 조건에서 다시 넣으며, 재처리할 때 원래 작업 ID를 유지할지까지 정해져 있어야 한다.

## 정상 실행보다 중간 종료를 먼저 시험해본다

이 설계가 목적대로 동작하는지는 성공 요청만으로 확인하기 어렵다. 작업 경계마다 실행을 끊어보는 테스트가 필요하다.

| 실행을 끊는 지점                   | 확인할 동작                                      |
| ---------------------------------- | ------------------------------------------------ |
| 외부 분석 완료 후 응답을 받기 전   | 결과를 확인하거나 안전하게 재시도하는가          |
| 결과와 outbox 기록을 저장한 직후   | 분석을 다시 하지 않고 알림 전달을 이어가는가     |
| 큐 전달 후 전달 완료 기록 전       | 중복 메시지를 받아도 허용 범위 안에서 처리되는가 |
| 워커 선점 만료 후 이전 워커가 복귀 | 이전 워커가 최신 상태를 덮어쓰지 못하는가        |
| 한 문서에서 영구 오류 발생         | 독립적인 다른 문서는 진행되는가                  |

여기에 재시도 중 입력이 수정되는 경우도 넣는다. 예전 입력으로 시작한 작업을 최신 입력의 성공으로 기록하면, 실행은 끝났어도 결과는 틀린 상태다. 작업 ID에 입력 버전을 넣는 설계가 실제 저장과 조회 경로에서도 유지되는지 확인해야 한다.

모든 자동화에 이 장치들을 처음부터 넣을 필요는 없다. 로컬 파일을 읽어 언제든 재생성할 수 있는 결과를 만드는 작업이라면, 완료 목록을 기록하는 것만으로 충분할 수 있다. 외부 과금, 사용자 알림, 긴 처리 시간, 여러 워커가 붙으면서 복구 비용이 커질 때 필요한 경계를 추가하면 된다.

문서 천 개 중 한 개가 실패하는 일은 앞으로도 생길 것이다. 그때 운영자가 해야 할 일이 로그를 뒤져 성공한 문서를 다시 추리는 일이어서는 곤란하다.

실패한 문서가 무엇인지, 어디까지 끝났는지, 다음 시도가 언제인지가 남아 있어야 한다. 다시 실행하는 버튼을 눌렀을 때 이미 끝난 일을 망가뜨리지 않을 근거도 있어야 한다.

그 정도가 되면 731번째 문서에서 멈췄다는 연락을 받아도, 천 개의 작업을 처음부터 의심할 필요는 없어진다.
